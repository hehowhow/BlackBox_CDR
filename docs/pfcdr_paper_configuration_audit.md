# PFCDR 论文、公开代码与本地实验设置核对

日期：2026-09-22。结论：早期 MF 版 PFCDR/EMCDR 的主要数值参数与公开代码默认值一致，
Book→Movie 的结果也接近论文 MF 结果。现有证据不支持将“输给物品均值”主要归因于

## 1. 先区分我们运行过的几类实验

| 实验 | 方法和目的 | 是否是论文 PFCDR |
| --- | --- | --- |
| 早期 PFCDR-WB | 官方 MF 预训练、条件反演、线性原型映射、目标用户投票 | 是，保留官方 MF 核心执行逻辑；有记录口径/RNG/工程适配差异 |
| 早期 EMCDR | 源用户向量线性映射到目标用户向量 | 是作者仓库提供的一个基线 |
| Top100 分数蒸馏＋PFCDR | 先从 API 提取替代源模型，再接 PFCDR | 自建黑盒替代方案，不是作者实验，也不是 DBGRME 复现 |
| LIST | Top100 源物品 ID/排名→池化→MLP→目标评分 | 自建方法，作者论文/仓库没有这个 LIST |
| 最近 Top100 残差 | 固定平滑物品均值＋源列表修正，配对打乱对照 | 自建诊断，不是 PFCDR 的参数改版 |
| 最后 MF 向量/历史统计残差 | 特权源表示替换 Top100，检验是否存在源域增量 | 自建诊断，不是 EMCDR/PFCDR/PTUPCDR 的复现 |

论文 PFCDR 的源端可以使用预训练模型、物品向量及输入梯度，反演出用户对应的原型，
跨域传输的是原型。它没有把源端限制为“只能拿到 Top100 物品 ID”。
因此，LIST 和 PFCDR 的区别首先是方法与可访问的信息，不只是学习率、维度不同。

论文中的 top-k 指 **目标域参与投票的用户数**；我们 API 的 Top100 指
**源域返回的物品数**。二者不是同一个参数，不能把 100 改成 70,000 就叫对齐论文。

证据：PDF 第 3–6 页 §4、Eq.(10)–(14)；
[官方模型](../external/PFCDR/models.py:163)、[LIST](../scripts/run_list_encoder.py:28)、
[残差模型](../scripts/residual_experiment.py:93)。

## 2. 哪些数值参数一致，哪些没有对齐

以下“早期”指实际用于效果比较的记录，不包括只检验程序能运行的 Slurm 8553。

| 项目 | 论文/公开实现 | 早期 PFCDR/EMCDR | 最近残差/表示诊断 |
| --- | --- | --- | --- |
| 原始数据 | Amazon 2014 三域完整 5-core；Table 2 | 相同来源、完整数据，无子采样 | 同一数据；Movie→Music 已清洗 |
| 骨干 | 主表 MF；另有 GMF、DNN | 只运行 MF | 源 MF＋自建残差学生 |
| 源/目标 MF 维度 | 10 | 10，一致 | 源 10；学生 32 是不同含义 |
| 预训练优化器 | Adam | Adam，一致 | 源/学生均 Adam |
| 预训练学习率 | 论文搜索 0.001/0.005/0.01/0.02/0.1；代码默认 0.01 | 固定 0.01，符合默认但未复现搜索 | 源固定 0.01；学生 0.001 |
| 预训练 weight decay | 代码 0 | 0，一致 | 源 Adam 默认 0；学生 1e-5 |
| 预训练 epoch | 代码默认 10；论文未列出各设置的具体最优轮数 | 每个域 10，记录确认 | 源 10 |
| 源/目标训练 batch | Book→Movie 512/512；Book→Music 512/512；Music→Movie 256/256 | Book→Movie 512/512 一致；两个自定义方向均采用 512/512 | 源统一 512，学生 2048 |
| EMCDR 映射 | 无偏置 10→10 线性层，向量 MSE，lr=0.01，batch=128，10 epoch | 相同 | 最后向量诊断不是这个 EMCDR |
| PFCDR 原型映射 | 无偏置 10→10，MSE，lr=0.005，10 epoch | 相同 | 不使用原型映射 |
| 原型映射 batch | 官方 Book→Movie/Book→Music 为 512，Music→Movie 为 1024 | wrapper 写死 512；匹配已跑的官方 Book→Movie，不能原样扩展到官方 task3 | 不适用 |
| 反演迭代/batch | 代码 300/200 | 配置 300/200，调用官方模块 | 不做反演 |
| 反演 lr/weight decay | 1e-4/1e-4 | 相同 | 不适用 |
| 反演目标评分 | 5 | 5，相同 | 不适用 |
| 反演 lr schedule | 代码 warmup 10＋cosine | 调用相同官方模块 | 不适用 |
| K | 论文研究 100/1000/10000/30000/50000/70000；MF 代码写死 70000 | 保留 70000，没有按新方向调节 | 无 PFCDR 用户投票 |
| 学生结构/目标 | PFCDR 对齐原型；EMCDR 对齐用户向量 | 按各自方法执行 | 32→64→32、dropout=0.1，直接拟合目标评分残差 |
| 评价指标 | MAE、RMSE | 两项均报告 | 两项均报告，主选模指标为验证 RMSE |
| 多次运行 | Table 1 十次运行均值 | 主要一个种子；Movie→Music 另有 seed2021 | 一个固定划分，三个训练种子 |

## 3. 任务方向确实不同

| 序号 | 论文与官方 config | 我们后续主要任务 |
| --- | --- | --- |
| 1 | Book→Movie | Book→Movie |
| 2 | Book→Music | Movie→Book |
| 3 | Music→Movie | Movie→Music |

第二组是不同任务，第三组是反向任务，不是换个名称。目标物品、目标用户、评分分布、
域间关系方向均不同，因此不能将这两组的差成绩直接解释成“未复现论文第二/第三组”。
`scripts/run_extra_tasks.py` 明确为两个新方向构造配置，虽然仍把 task 字段写为 1。

原始统计与 Table 2 一致：Books 8,898,041 条、Movie 1,697,533 条、Music 1,097,592 条。
本轮审计未发现“下载了错误版本/少了大量数据”这一类证据。
清洗后的 Movie→Music 有 17,874 个重叠用户，不能再与未清洗的 18,031 人协议直接混比。

## 4. K 的实际执行值是一个具体、可疑的迁移设置

官方 config 的三个 K 分别为 85,000、50,000、85,000，但
[MF forward 第 181 行](../external/PFCDR/models.py:181) 实际重新设置 `topk = 70000`，
忽略 `self.topk`。本地[缓存投票实现](../scripts/experiment.py:222)也固定截取 70,000。
仅修改 `config.json.topk` 或 `first_round.json.voting_topk` 不会改变这些实际计算。

| 早期任务 | 目标用户总数 | K | 每次候选用户的选取比例 |
| --- | ---: | ---: | ---: |
| Book→Movie | 123,960 | 70,000 | 56.47% |
| Movie→Book | 603,668 | 70,000 | 11.60% |
| Movie→Music | 75,258 | 70,000 | 93.01% |

对于 Movie→Music，任意两个大小为 70,000 的投票集合，至少共享
`2×70,000−75,258=64,742` 人，即各自投票成员的至少 92.49%。这是集合大小直接给出的下界，
不需要重新训练就能确定。相同成员的大量平均可能稀释个性化；它不等价于已经测得预测相同，
也不证明全部误差都由 K 导致。

PDF 第 8 页 Figure 3/§5.4.1 明确认为 K 需要调，Book→Music 在约 10k–30k 较好。
我们没有运行这个官方方向，因此不能直接宣称 Movie→Music 的最优 K 也一定是该范围。
但将同一个 70k 从 Movie 目标域搬到 Music/Book 目标域，确实缺少验证依据。

另一个继承自官方代码的问题：投票候选来自整个目标用户 embedding 表，
包括没有接受目标训练的冷用户行。它们不一定实际被选中，但没有被排除。
是否及多大程度损伤预测，需有对应权重和投票结果才能量化。

PFCDR 的“投票平均”是平均多个目标 MF 用户对物品的**模型预测**，
不是平均该物品已有的**真实训练评分**，所以不能认为 K 很大就会自动得到我们的强物品均值基线。

## 5. 选模口径不同，但已有记录表明这解释不了均值差距

官方 `Run.update_results` 在每一轮测试后，分别保留最低测试 MAE 和最低测试 RMSE；
这两项甚至可能来自不同轮次。公开路径没有独立验证集。
论文说明十次均值，但没有充分交代网格搜索使用什么选择集，不能据代码进一步断言论文每个结果的选模细节。

我们早期报告固定第 10 轮；后续用验证集选 epoch。这些评价口径不能直接混合。
这里仅描述性地读取历史十轮记录的最小值，**不把它们改报为新的正式结果**。

| 本地历史任务 | PFCDR 第10轮 MAE | 十轮最低测试 MAE | 同一历史协议的物品均值 MAE |
| --- | ---: | ---: | ---: |
| Book→Movie | 0.967869 | 0.963388（第8轮） | 0.833428 |
| Movie→Book | 1.077062 | 1.076896（第5轮） | 0.787448 |
| Movie→Music（旧污染版本） | 1.639227 | 1.639089（第2轮） | 0.741995 |

三组即使取较乐观的历史最好轮，也仍未超过均值。EMCDR 的历史最低 MAE 分别为
1.164872、1.119263、1.567097，同样未超过各自均值。
因此能直接排除“仅仅因为固定最后一轮，才造成均值胜出”这一单一解释。

## 6. Book→Movie 的 MF 结果实际上接近论文

这是当前唯一方向一致、可以初步核对量级的任务，β=20%。

| 方法 | 论文 Table 1 MAE | 本地第10轮 MAE | 本地十轮最低测试 MAE |
| --- | ---: | ---: | ---: |
| TGT | 4.1831 | 4.178897 | 4.178897 |
| EMCDR | 1.1651 | 1.176062 | 1.164872 |
| PFCDR | 0.9579 | 0.967869 | 0.963388 |
| 物品均值 | 未列入论文对照 | 0.833428（无训练轮次） | 不适用 |

PFCDR 的 RMSE：论文 1.2437，本地最后一轮 1.243124，数值也接近。
这支持当前 MF 实现并非严重跑偏；但论文为十次均值，本地主要一个种子且分割实现/RNG存在差别，
不应称为精确复现，也不能把论文模型与本地均值的跨实验数值差当作严格配对胜负。

真正可以严格说的是：在我们的同一测试上，接近作者 MF 效果量级的 PFCDR 明显输给物品均值。
论文 Table 1 没有物品均值/中位数对照，因此论文报告胜过其选定方法，不等于保证胜过这个强基线。
官方 TGT 对冷用户使用未训练的目标用户向量，没有均值回退；这也解释了其 4 左右的很差 MAE。

## 7. 骨干与调参覆盖仍然不足，但不是已证实的原因

论文不仅跑 MF，还在 Figure 2 比较 GMF 和 DNN。Book→Movie 上 PFCDR 的图示 MAE
分别约 0.958、0.867、0.802，说明骨干选择在作者实验中有很大的影响。
这比已量化的最后轮/最好轮差异更值得后续验证。
但不能用 0.802 对我们不同种子/协议的均值 0.833428 直接宣称 DNN 已经在本地获胜。

我们的 MF 学习率固定为 0.01，未完成论文描述的五档网格搜索。
论文/公开配置未提供每任务、每骨干的最终最优学习率及完整选择记录，
只能说对齐了公开默认值，不能说对齐了作者全部调参结果。

当前 wrapper 主要面向 MF：`inverse()` 将 base_model 固定写为 MF，
原型路径固定 `5_MF`，缓存投票访问 MF 的 `tgt_model.uid_embedding`，没有处理 DNN 的用户变换层。
所以不能仅把 JSON 改为 DNN/GMF 就认为已得到正确的作者模型；需要先适配并核对官方前向。
同理，当前目标评分和路径也存在固定 5 的逻辑，不能仅改反演目标评分就完成该消融。

## 8. 论文与代码自身的差异

1. PDF 第 7 页参数段和 Figure 1 写反演损失为 BCE；Eq.(9)/(10)、Appendix A 写平方误差，
   公开 `Inversion.criterion` 使用 `MSELoss`。本地沿用公开 MSE。
   这是论文内部/文码不一致，不能认定为我们把作者代码改错；尤其不能对目标评分 5 直接套普通二元交叉熵。
2. Eq.(5) 的符号写 `U(0,1)`，紧接的文字写 Normal；代码用 `np.random.randn` 后 softmax。
   本地调用官方初始化，符合后者。
3. Algorithm 1 以反演损失阈值 ε 停止；公开代码固定 300 次、保留 batch 最低损失对应输入，
   使用 warmup/cosine。论文未给出可直接照搬的具体 ε。
4. 论文分析/调节 K，config 写不同值，但 MF forward 写死 70k，DNN 也写死 70k、GMF 写死 50k。
5. README 写默认 task1，`main.py` 实际默认 task3；准备数据循环还包含 config 不存在的 task4。
   本地采用显式入口避开这些问题。它们不改变已经成功运行的 Book→Movie 结果。

## 9. 后续验证协议和公平性差异

最近的 60/20/20 是重叠用户的训练/验证/测试比例；目标独有用户仍在训练中。
作者代码 β=20% 对应重叠用户 80/20 的二路划分。
Book→Movie 目标训练评分从 1,541,404 降至 1,381,412，减少约 10.38%；
可用于跨域监督的重叠训练用户从 29,910 降到 22,432，减少约 25%。
这可能影响成绩，但不是泄漏或实现错误，也不是把验证用户重新混入训练的理由。

清洗、独立验证、固定基线、epoch 0 和真实/打乱对照，都是为诊断可信性加入的控制。
最近两个有效源表示和失败的 Top100 残差使用相同新划分、同一批源模型，
所以这些共同变化不能单独解释它们之间的性能差异；但模型前端/训练参数量差异仍阻止严格单因果归因。
最新三个训练种子不是三个新数据划分，历史测试集也已经使用过，因此结果仍是探索性的。

即使 seed 都写 2020，旧 wrapper 在不同阶段重设 RNG、跳过/补跑 EMCDR 的次序，
以及新版源服务的显式 GPU shuffle，都不会与作者整段进程逐步消耗相同随机数。
Python 的 set 枚举、版本和 PYTHONHASHSEED 也会影响原始 ID 映射。
这些限制精确复现，但没有证据说明它们足以造成当前巨大的均值差距。

## 10. 对用户问题的回答与下一步

**是否一致：部分一致。** 早期 MF/PFCDR/EMCDR 常用超参数匹配公开默认值；
任务方向、骨干覆盖、学习率/K 搜索、选模/重复次数与论文完整实验不一致；
后续 LIST/残差诊断本来就是不同方法。

**是否由不一致导致无法利用源域：尚不能作统一因果判断。**
Book→Movie 的 MF 成绩接近作者、最好轮仍输均值，已有证据反对“主要是基本参数配错”。
对自定义 Movie→Music，70k/75k 的投票设置有明确的过度平均嫌疑。
更强骨干和合理学习率搜索有改善可能，幅度需验证。

这次阅读没有推翻上轮“存在源信息增量”的结果，但应将表述限定为当前三组评分预测。
它没有证明原 PFCDR 实现一定训练坏了，也没有证明 Top100 信息本身完全无效。

如果继续实验，建议从下面两个有明确问题的方向择一开展，避免立刻铺开大网格：

- 若优先回答“能否在作者方法上超过均值”：先做方向一致的 Book→Movie，
  同一合法验证协议下比较 MF 与论文 DNN 骨干，加入物品均值、平滑均值和中位数。
  先适配 DNN 反演/投票与配置传递，再验证官方前向；预训练学习率只在验证集作有限搜索，
  不把作者最低测试指标作为选择规则。表现接近论文也必须与本地同划分基线比较。
- 若优先定位 Movie→Music 的异常大误差：在清洗后的同一划分重新训练合法源/目标模型，
  固定权重/原型/映射后用验证集比较少数 K，例如 1k/10k/30k/70k。
  第一阶段保留官方候选池，只改变 K；若再排除未训练候选，应另设对照，避免两个因素一起改。
  历史权重未上传，因此目前不能声称只需读一次旧 checkpoint 就能完成该实验。
